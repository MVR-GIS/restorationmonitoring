# DuckDB reporting and publication direction

The user selected DuckDB as the authoritative **development reporting store** and GeoPackage as the preferred import format for the available GIS exports. Restoration Features and UMRR-DB remain authoritative in their own domains; their DuckDB tables are versioned source snapshots, not a replacement system of record. EMMA remains the target application for the proposed integration component. Enterprise database technology, approval and deployment remain separate decisions.

On 2026-11-06 the user clarified the delivery sequence: use static pkgdown reports while iterating on the model and prototypes; once approved, populate an authoritative database that drives a dynamic partner-facing application for analysis. The production engine, operating environment, synchronization, access controls and deployment are not yet chosen or approved. The user also requested retirement of development JSON data fixtures in favor of explicitly modeled DuckDB records; original evidence and migration inputs must be reconciled before removal.

Reports should read modeled content from the designated DuckDB snapshot and record its fingerprint and generation time. GeoPackage imports should retain source/layer identity, source hash, feature counts and CRS. Reviewed source worksheets, documents and historical HTML remain evidence and migration inputs; they do not become disposable just because a database exists. Avoid multiple independently maintained copies of the same modeled fact. Until records have been migrated and reconciled, legacy reports are historical prototypes, not DuckDB-backed reports.

This is a development direction, not a production readiness claim. The current build creates a **new** database from a small, curated science fixture plus source exports; it is not a safe refresh mechanism for manually authored findings or decisions. Incremental ingestion, durable backup, versioning, migration, update conflicts, permissions and enterprise deployment require design and testing. Do not rebuild over a database containing unique new work. `dev/outputs/` is ignored by Git and is not a backup.

## Reporting choices

| Approach | When data is queried | Interaction | Hosting and tradeoff |
| --- | --- | --- | --- |
| Pre-rendered R Markdown/Quarto | R reads DuckDB locally at render time | Links, search, maps and JavaScript widgets can work on already delivered data | Static HTML on GitHub Pages through pkgdown; repeat local render/publish to refresh. No live database access. |
| Browser-side selection | R queries DuckDB at render time and embeds selected public data or precomputed views | Controls filter or switch among data already sent to the browser | Static hosting, no R server. Download size, browser resources and information exposure increase with data. |
| Browser SQL with DuckDB-Wasm | Browser queries a separately delivered public dataset during viewing | Flexible client-side filtering and exploration | Can run on static hosting, but requires JavaScript integration and testing of data distribution, browser limits, spatial support and deployment headers. It does not directly query the developer's local DuckDB file. See [DuckDB-Wasm](https://duckdb.org/docs/stable/clients/wasm/overview). |
| Shiny or Quarto with Shiny | R server queries its accessible database during a session | Selectors can request new results without precomputing every view | Requires an R host; [Posit Connect Cloud](https://docs.posit.co/connect-cloud/user/index.html) supports R Shiny, Quarto and R Markdown. Database access, refresh, concurrent access, deployment and durability must be designed for the actual service. |

[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site) serves static files, not an R/Shiny server. `pkgdown` organizes and publishes documentation and rendered reports; Quarto/R Markdown produce reports, and Shiny adds server-side reactivity. They are complementary. Any embedded data or browser-delivered data on a public site is accessible to its readers; publish only appropriate derivatives. [Connect Cloud sharing](https://docs.posit.co/connect-cloud/user/share/index.html) varies by plan.

## Migration status

The three-entry Bertom report reads study, findings and candidate associations from DuckDB and now prefers the full GeoPackage Revetment layer when present; it labels a legacy XML fixture fallback. It renders static snapshots. Its query is limited to a single feature class and candidate project-number match, not complete spatial discovery.

The exported Steamboat `research_question_summary()` and related worksheet reports still read JSON and use information not yet represented by the current DuckDB schema and fixture. The older Bertom evidence walkthrough, client-side multi-entry and FWWG visualization also contain curated data assembled outside DuckDB. Keep these explicitly historical during migration. Inventory their data and provenance, expand the relational model, import and reconcile the underlying records, and compare report content before replacing each one. Do not pretend all reports are migrated or silently drop unique evidence.

An initial relational migration is available in `dev/outputs/duckdb/restoration-research-aligned-v5.duckdb`: `research_register` contains 49 workshop questions, 196 reach ranks, 20 project marks, four proposed pilot links, six scientific sources, eight scientific assertions and two derivation links alongside the full GIS snapshot. [DDL](../schemas/duckdb-research-registers.sql) defines the source-specific tables; the [one-time migration](../scripts/duckdb-migrate-research-registers.R) records input fingerprints and checks the workbook hash. The workbook questions, source cells, ranks, assertion wording and statuses were reconciled in tests. These are review-local records, not approved EMMA entities. The [research alignment](research-questions-evidence-relational-design.md) maps WQ-39 and SC-08 to the earlier prototype and adds source-independent relationships. Report renderers still use their existing inputs.

The [Steamboat planning slice](steamboat-planning-extraction-duckdb.md) preserves its four objectives, eleven planned criteria, targets, five trigger groups, source locators and open discrepancies in relational tables. It stays separate from older pilot objective/criterion records, with two source-backed **proposed** mappings that make wording and scope differences visible. The [DuckDB-backed Steamboat report](../features/steamboat-duckdb-report.md) also displays the ten-part Newton evidence chain, flags and file records. The latest local database is `dev/outputs/duckdb/restoration-steamboat-reconciled-v1.duckdb`.

This is an incomplete migration: workbook check metadata and science worksheet context, the 40-document register and other curated report fixtures still require relational mapping and content reconciliation. The earlier exported Steamboat report API still uses JSON; the new DuckDB-backed report is a separate development workflow. The original JSON files remain migration evidence and active report dependencies. The migrated local database is ignored by Git and must not be treated as a durable backup or a reproducible replacement until a safe storage and update strategy is implemented. The earlier migration-v1 copy lacked GIS tables because a plain file copy missed the source WAL; use the corrected migration-v3 and aligned-v5 copies. The corrected scripts checkpoint and copy to new destinations; disconnect other processes before copying.

Recommended first publishing increment: generate multiple linked static views from one named DuckDB snapshot, then add browser-side navigation and visualizations for a bounded, publishable evidence set. This uses the existing manual pkgdown/GitHub Pages workflow, with no GitHub Actions. Evaluate Shiny only when live, server-side filtering or controlled access justifies its operations; DuckDB-Wasm is an optional later experiment, not a prerequisite.
